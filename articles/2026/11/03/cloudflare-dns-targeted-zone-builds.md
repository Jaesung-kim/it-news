# 클라우드플레어, DNS 빌드 지연 절반·메모리 85% 절감…'필요한 부분만 다시 빌드'

- 출처: Cloudflare 블로그, GeekNews
- 원문: https://blog.cloudflare.com/dns-targeted-zone-builds
- 발행일: 2026-11-02

## 상세 요약

클라우드플레어가 DNS 레코드와 존 설정 변경을 권한 DNS 서버용 데이터로 바꿔 분산 키-값 저장소 퀵실버(Quicksilver)에 쓰는 'Zone Builder' 파이프라인을 개편한 과정을 공식 블로그에 공개했다. 핵심은 변경으로 영향을 받는 부분만 다시 빌드하는 플래너와 통합 스케줄러다.

기존에는 일부 존 설정이 바뀌면 존 전체를 다시 빌드해야 했다. 처리해야 하는 이벤트는 2022년 초당 약 250건의 레코드 변경에서 약 700건과 기타 이벤트 약 100건으로 늘었고, 레코드가 2000만 개를 넘는 존도 있어 전체 빌드는 확장성에 한계가 있었다. 레코드 단위 빌드는 2022년에 이미 도입했지만, 유니버설 SSL처럼 존 최상위(apex)의 CAA 레코드를 바꿀 수 있는 존 설정 이벤트는 무엇이 바뀌었는지 알기 어려워 대상을 좁히기 힘들었다.

새 방식에서는 이벤트에 바뀐 필드와 이전·새 값을 함께 담고, 빌드를 '리소스만', '리소스와 메타데이터', 'apex와 메타데이터', '삭제(purge)', '전체 존' 다섯 종류로 나눈다. 대상 빌드가 쓰는 모든 키는 전체 빌드가 썼을 결과와 바이트 단위로 같아야 한다는 원칙을 세웠다. 플래너는 이벤트로 보수적인 작업 목록을 만든 뒤, 실행 직전 데이터베이스 복제본에서 최신 상태를 다시 읽어 계획을 확정한다. 지연된 복제본에서 읽은 값은 거부한다. 회사는 "플래너는 불확실성을 결코 작업량 감소로 바꾸지 않는다"고 설명했다.

통합 스케줄러는 같은 존에 쌓인 작업을 하나로 합치되, 전체 빌드가 하나라도 필요하면 전체 빌드로, 삭제가 있으면 삭제를 우선한다. 카프카 메시지 완료는 별도로 추적해, 빌드가 순서와 상관없이 끝나도 앞선 메시지가 모두 끝난 뒤에만 오프셋을 커밋한다. 재시작 시 미완료 작업은 다시 실행하는데, 변경을 잃느니 작업을 반복하는 쪽을 택했다고 밝혔다.

검증을 위해 같은 DB 상태에서 전체·대상 빌드 결과를 바이트 단위로 비교하는 테스트와, 운영 이벤트를 받아 별도 환경에 쓰는 미러 빌더를 운영했다. 23만 4313개 존을 비교한 결과 차이는 0.31%였고 대부분 타이밍 문제였다.

결과적으로 빌드의 92.95%가 전체 빌드를 피했고, 전체 빌드 비율은 11.88%에서 7.04%로 약 40% 줄었다. 최대 메모리는 79GiB에서 12GiB로 85%, 평균 메모리는 49GiB에서 7GiB로 86% 감소했다. 빌드 완료 지연 중앙값은 약 7.7초에서 3.3초로 절반 이하가 됐고, p99 지연 최대 급등치는 14.6분에서 1.21분으로 줄었다. 다만 이 지연 수치는 퀵실버의 네트워크 전파 시간을 뺀 값이며, 첫 게시나 존 전체에 영향을 주는 변경에는 여전히 전체 빌드가 필요하다.

## 핵심 포인트

- 변경 영향 범위만 다시 빌드하는 플래너와 통합 스케줄러를 도입했다.
- 전체 빌드는 약 40% 감소했고, 빌드의 92.95%가 전체 재빌드를 피했다.
- 최대 메모리 79GiB→12GiB(85%↓), 지연 중앙값 7.7초→3.3초로 줄었다.
- 대상 빌드 결과는 전체 빌드와 바이트 단위로 같아야 한다는 원칙으로 정확성을 검증했다.
- 전체 빌드를 완전히 없애는 것은 현실적이지 않다고 인정했다.
